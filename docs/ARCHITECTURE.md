## 1. What Helpdesk is

A multi-tenant SaaS help desk sold per agent, competing with Zoho Desk and Freshdesk. Each customer company gets its own workspace (for example `acme.helpdesk.example.com`). The workspace's agents handle support tickets that its own customers raise by email or web form.

### Release 1 scope

| #   | Area                   | Contents                                                                                                                                                                                                                                               |
| --- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | Ticketing              | Ticket number, statuses (Open, Pending, Waiting on customer, Resolved, Closed), priority, type, tags, custom fields; list, view, filters, search, history, attachments; reply, forward, private notes, @mentions, collision detection; merge and split |
| 2   | Channels               | Email-to-ticket (threaded), embeddable web form                                                                                                                                                                                                        |
| 3   | Assignment and routing | Agents and roles (Admin, Supervisor, Agent), teams, manual and round-robin assignment, assignment rules (keyword, customer field, default team), contacts and companies with custom fields                                                             |
| 4   | SLAs and escalation    | Policies by priority, business hours, holidays, warning before breach, escalation on breach, email and in-app notifications                                                                                                                            |
| 5   | Automation             | Canned responses with placeholders, event-based rules, time-based rules                                                                                                                                                                                |
| 13  | Product foundation     | Sign-up, workspaces, subdomains; branding and custom "from" address; plans, trials, Stripe billing, invoices; 2FA, password policy, audit log, HTTPS, backups; responsive web app                                                                      |

### Why not Lambda for the API

The company's other APIs run on Lambda, but Helpdesk's API and worker need long-lived processes:

- WebSockets for collision detection and live updates (Lambda only works with API Gateway WebSocket APIs, which need connection bookkeeping and per-message billing).
- Always-on job polling for SLA timers and time-based rules.
- At steady load, an always-on container costs less than the same compute on Lambda.

Lambda can still be used later for small event-driven side tasks (for example virus-scanning an uploaded attachment from an S3 event).

### How we choose the compute service

Decided in this order. Each step narrows the options:

1. **Technical fit:** the API holds WebSocket connections and the worker runs continuously, so both need long-running processes. That rules out Lambda for them.
2. **Network:** in prod the database sits in private subnets. Fargate runs inside our VPC; Lightsail containers sit outside it and can only reach a private RDS through VPC peering with the default VPC.
3. **Availability:** prod needs at least 2 API copies across availability zones with automatic replacement, plus autoscaling.
4. **Load:** measured as concurrent logged-in agents (WebSocket connections), API requests per second, and jobs per minute. Customer count matters only through these numbers.
5. **Cost and simplicity:** fixed monthly price and fewer moving parts win where steps 1–4 allow it.

Applied to each environment:

| Environment | Choice                                                    | Reason                                                                                                                                                                                                                                                                           |
| ----------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Local       | Node on the developer machine                             | Fastest feedback                                                                                                                                                                                                                                                                 |
| Dev         | ECS Fargate in the VPC, small (on-demand, always on, ARM) | Same CDK stack as prod with smaller settings, so there is one hosting setup to maintain and dev catches network or scaling problems before prod. ARM keeps the cost down; no Spot or off-hours schedule, so dev stays available (see the cost-savings rule in the decisions log) |
| Prod        | ECS Fargate in the VPC                                    | Private database access, multi-AZ, autoscaling                                                                                                                                                                                                                                   |

Lightsail containers were considered for dev. They were rejected because they would be a second, different hosting setup (CDK only offers low-level support for them) for a saving of roughly $10–20/month.

Move from one setting to the next when load testing or CloudWatch shows sustained CPU above ~60–70%, memory pressure, or WebSocket connections approaching the per-task limit measured in our load test.

### Environment configuration and infrastructure as code

Switching environments is a matter of settings, never code:

- **One Docker image** for `api` and `worker`, identical in every environment.
- **All settings come from environment variables,** validated once at startup in `helpdesk-api/src/config` (Zod). The app refuses to start if a setting is missing or invalid. `.env.example` lists every variable.
- **Adapters, chosen by setting:** `EMAIL_DRIVER=smtp|ses`, `STORAGE_DRIVER=local|s3`. Feature code calls the adapter interface and never checks which environment it's in.
- **Database switch:** change `DATABASE_URL` and run `npm run db:migrate`.
- **AWS infrastructure in code:** `helpdesk-api/infra/` is an AWS CDK app (TypeScript) that defines all AWS resources, including the S3 bucket and CloudFront distribution the frontend deploys into. The same stacks (network, database, app, web hosting) deploy to dev and prod; only `infra/config/dev.ts` and `infra/config/prod.ts` differ (sizes, task counts, Spot, schedules, Multi-AZ).
- The frontend's settings (`VITE_*`) are build-time values set per environment in its pipeline.
- Logs go to standard output; `/health` is the health check used by the load balancer and ECS.

### Scaling notes

- With more than one API task, Socket.IO needs a shared adapter: we use `@socket.io/postgres-adapter` (no Redis). The ALB needs sticky sessions.
- Workers can run several copies; pg-boss guarantees each job runs once.
- Redis (ElastiCache) is added only if real load measurements show a need.

## 4. Multi-tenancy and data isolation

- Every tenant-owned table has a `workspace_id` column.
- **Layer 1, application:** every request resolves the workspace from the subdomain plus the logged-in user's membership; every Sequelize query is scoped to it.
- **Layer 2, database:** PostgreSQL **row-level security** policies on every tenant table, `USING (workspace_id = current_setting('app.workspace_id')::uuid)`. The API sets `SET LOCAL app.workspace_id` at the start of each request transaction. A forgotten `WHERE` clause still cannot leak another company's data.
- The app connects as a database role **without** `BYPASSRLS`. Migrations run as a separate owner role.
- **Global tables:** `users` (one person, one login, who can belong to several workspaces) and `workspaces` (looked up by address before any workspace is known) are not owned by a workspace, so they have no row-level security; nor do the person-level `password_history`, `password_resets` and `login_failures`. Every workspace-owned table has it, starting with `memberships`. Sessions and email links are looked up only by the hash of a secret token.
- **Audit log:** `audit_events` is a workspace table with row-level security, insert-and-read only for the app role. A person's own security events are written into each workspace they belong to.
- **Members and invitations:** `invitations` is a workspace table with row-level security (one open invitation per email per workspace). Memberships carry a status: deactivated members stay on past tickets but cannot sign in to that workspace (no hard delete in Release 1).
- **Two-step verification tables** (`user_two_factor`, `recovery_codes`, `login_challenges`, `trusted_devices`) also belong to the person and have no row-level security; `workspaces.require_two_factor` is the workspace's rule.
- **Teams (F8):** `teams`, `team_members` and `invitation_teams` are workspace tables with row-level security; `team_members` references `memberships (workspace_id, user_id)`, so a team can only hold members of its own workspace.
- **Tickets (F9):** `tickets`, `ticket_tags`, `ticket_activities` and `ticket_counters` are workspace tables with row-level security. A ticket's assignee and creator reference `memberships (workspace_id, user_id)`; its requester references `contacts` (deleting a contact with tickets is refused).
- **Saved views (F10):** `ticket_views` is a workspace table with row-level security; a view belongs to a member (`memberships (workspace_id, user_id)`) and may be shared with the workspace.
- **Conversation (F11):** `ticket_messages` and `ticket_attachments` are workspace tables with row-level security; files live in file storage under `<workspace id>/<file id>`.
- **Notifications (F25):** `notifications` is a workspace table with row-level security; each row belongs to one member (`memberships (workspace_id, user_id)`) and the API only ever reads the signed-in member's own. Email choices are on `memberships`.
- **Merge (F28):** `tickets.merged_into_id` points at a ticket of the same workspace; moved messages keep `from_ticket_number`.
- **SLA policies (F23):** `sla_policies` is a workspace table with row-level security; a ticket's due times live on `tickets`.
- **Business hours (F22):** `business_hours` (one row per workspace) and `holidays` are workspace tables with row-level security.
- **Own memberships:** `memberships` also has a read-only `own_memberships` policy (`user_id = app.user_id`), so "find your workspace" can list one person's workspaces without bypassing row-level security.
- Automated tests try cross-tenant reads and writes on every endpoint and must fail.

## 5. Authentication and authorization (architecture level)

- **Sessions:** server-side sessions stored in PostgreSQL (only a hash of the token); the browser holds an `HttpOnly`, `Secure`, `SameSite=Lax`, host-only cookie, so a sign-in on `acme.helpdesk.example.com` is never sent to another workspace's address. No tokens in `localStorage`. A new session ID on every login; sessions end after 8 hours idle or 7 days, whichever comes first (settings); every session ends when the password changes; signing out deletes the session on the server and reloads the app.
- **Same address for the API:** the browser calls `/api` on the address it is on (`acme.helpdesk.example.com/api/...`). Locally the Vite dev server forwards it to the API; on AWS CloudFront forwards `/api/*` to the load balancer. Cookies stay first-party, the API knows the workspace from the host, and the app needs no CORS.
- **Passwords:** Argon2id hashing; password policy: at least 12 characters, breached-password check, not one of the last 5. Reset links are single-use, expire after 1 hour, are stored as hashes, and never sign the person in.
- **2FA ("two-step verification" in the app):** TOTP authenticator apps only (no SMS or email codes), plus 10 one-time recovery codes (hashed). Turning it on needs the password, the first code, and saving the recovery codes, and signs out other devices. Login asks for the code after the password; no session exists before the code is right; wrong codes count toward the login lock; an optional trusted device skips the code for 30 days. Admins can require it for the whole workspace (Settings → Security), enforced by the API on every request. Secrets are encrypted with AES-256-GCM.
- **Sign-up and invites:** email verification links and agent invite links are single-use, time-limited, and stored only as hashes.
- **Brute-force protection:** rate limits per IP on every auth endpoint; 5 failed logins for one email within 15 minutes lock it for 15 minutes, counted whether or not the email has an account (2FA adds its own limits in F3).
- **Roles:** Admin, Supervisor, Agent, fixed in Release 1 (custom roles in Release 2). Admins do everything; supervisors run the floor (all tickets, assign to anyone, merge, delete contacts and companies, shared canned replies, view members and teams); agents work tickets and add and edit contacts and companies. Everyone saves private ticket views; admins and supervisors share them (F10). A single role-to-permission table in code; every endpoint checks one permission on the server, and `/me` returns the list so the UI hides what a role cannot do. Only admins invite people, manage teams and change settings. The owner cannot be demoted or deactivated, and a workspace always keeps one admin.
- **Re-authentication:** making someone an admin, deactivating, and resetting two-step verification need the password confirmed on the session within 10 minutes (signing in counts).
- **Invitations:** by email, single-use 7-day links stored as hashes; new people choose a name and password, people with a Helpdesk account join with their password (and code).
- **CSRF:** SameSite cookies, a same-origin check on every state-changing request (`Sec-Fetch-Site` and `Origin`), plus a CSRF token on every signed-in change: derived from the session secret, returned with `/me`, sent back in `X-CSRF-Token`.
- Detailed screen-level flows are decided when the auth feature is built.

## 6. Security design

### Code level

- Server-side validation of all input (Zod); parameterized queries only (Sequelize, no string-built SQL).
- Secrets the server must read back (authenticator secrets) are **encrypted** with AES-256-GCM using a key from SSM (`TWO_FACTOR_ENCRYPTION_KEY`), with a key ID stored beside each value for future rotation.
- Ticket email HTML is **sanitized** (DOMPurify on the server) before storage and display; strict Content-Security-Policy.
- Attachments: size and type limits, stored in private storage, served only through short-lived signed URLs, never executed or served inline from the app's domain.
- Security headers through Helmet (HSTS, CSP, X-Frame-Options, Referrer-Policy). Pages may not be framed, except the public web form at `/support` (F16), which other sites embed.
- Secrets only in environment variables or Secrets Manager; `.env` is git-ignored.
- Dependency scanning (`npm audit` / Dependabot) and static analysis (ESLint security rules, Semgrep) in CI.
- **Audit log:** who changed what and when (members, security, settings and sign-ins from F5; rules, SLAs, deletions and the rest as they are built), written in the same transaction as the change. Append-only at the database level: the app role cannot update, delete or truncate `audit_events`. Admins read it in Settings → Audit log and export it as CSV (formula cells made safe).
- Stripe webhooks verified by signature; email ingest de-duplicated by `Message-ID` and protected against mail loops and auto-replies.

### Infrastructure level (AWS)

- HTTPS everywhere (ACM certificates); the database sits in private subnets with no public access in prod.
- Least-privilege IAM roles for each container; S3 buckets private with block-public-access on.
- Encryption at rest (RDS, S3) and in transit.
- AWS WAF in front of CloudFront and the ALB (rate limiting, common attack rules) before prod.
- Backups: RDS automated backups with point-in-time recovery, plus a tested restore procedure.

### Testing

- Automated: tenant-isolation tests, permission tests for every endpoint, end-to-end tests for each Release 1 use case.
- Before prod: an OWASP Top 10 review and an external penetration test (web app + API + AWS configuration).

## 7. Key data flows (technical)

**Incoming email → ticket**
Local and temporary dev: email lands in Mailpit → the `worker` picks up what is addressed to `TICKET_EMAIL_DOMAIN` (`INBOUND_EMAIL_DRIVER=mailpit`), stores the raw email and adds an `inbound-email` job. AWS (Step 0b): customer mail → SES receiving rule → raw message to S3 → the same job. The job parses it → drops duplicates (Message-ID), automatic email and loops → threads by `In-Reply-To`/`References`, then the signed reply address → new ticket or a customer message (reopening the ticket) → rules engine (F17) → assignment → SLA timers start → notifications.

**Outgoing reply**
Agent sends a reply in the UI → `api` stores the message with its Message-ID and adds a `ticket-email` job in the same transaction → `worker` sends it through the email adapter (SMTP to Mailpit, or SES) from the workspace's address (`acme@TICKET_EMAIL_DOMAIN`, with its sender name), with Reply-To `acme+<ticket>-<signature>@…`, In-Reply-To/References and the files → the message is marked sent, or failed after 5 tries (then **Send again**).

**SLA timer**
A ticket is created or changed → in the same transaction the first matching SLA policy works out the reply and resolve due times from creation, in business hours (leaving holidays and waiting-on-customer stays out) or round the clock, and stores them on the ticket with the next running deadline (F23) → with them the next warning or escalation time (`tickets.sla_alert_at`) → the `worker` checks every minute for the tickets whose time has come (F24): warn the assignee before the deadline; at it mark the ticket overdue, reassign it if the policy says so and tell the team's leads, each once per ticket and clock.

**Sign-up (F1)**
Sign-up form on the main address → `api` creates the person, a pending workspace and the owner membership → email job sends a single-use link (24 hours, stored as a hash) through Mailpit or SES → the link opens on the workspace's own address → `api` activates the workspace, starts the trial, creates a session and sets the cookie → the owner lands on the welcome page signed in as Admin.

**Login and password (F2)**
Login on the workspace address → `api` checks the lock for that email, the password and the membership → new session and cookie. Forgot password → single-use reset link (1 hour, stored as a hash) emailed for that workspace → new password (breach check, not one of the last 5) → every session ends → "password changed" email → login.

**Invitation (F4)**
Admin invites an email with a role → `api` stores an invitation (hash) and emails a link to the workspace address → the person opens it → new: name and password; existing: password (and code) → membership created, invitation used → signed in.

**Login with two-step verification (F3)**
Password accepted → `api` creates a 5-minute challenge (hash stored, HttpOnly cookie on `/api/v1/auth`) and answers 202 → the person enters an app code or a recovery code → `api` checks it (each code once; wrong codes count toward the lock) → session and cookie, plus an optional 30-day trusted-device cookie.

**Live updates (F26)**
A change is saved (by the `api` or the `worker`) → in the same transaction `NOTIFY helpdesk_live` carries a short signal ("ticket 42 changed", "a notification for Neha") → each `api` task listens and passes it over Socket.IO to its own browsers in the rooms per workspace, member and open ticket → the browser reloads that part through the REST API. Broadcasts between browsers ("Neha is replying…", F27) go through the PostgreSQL adapter to every `api` task.
